## Throw mechanic v1

1. The board fills the top 60% of a `100dvh` column. A 48px translucent score strip sits over it (remaining, darts left in
   the turn). The bottom 40% is one full-width **release pad**, with a 12px dead gap above it and `safe-area-inset-bottom`.
2. **Aim:** tap any visible bed. The target snaps to that bed's centre and the board zooms to about 2x around it. The target
   is **sticky**: it stays for the next dart. A 44px "Whole board" chip zooms out to pick a far bed.
3. **Wobble:** a crosshair drifts around the target on a two-harmonic figure-8 path (a circle option exists for the Lab).
4. **Release:** a tap on the pad, handled on `pointerdown`. Taps on the board only re-aim; they can never throw. After a
   re-aim, release is ignored for about 200ms. After a throw, the pad is inert for about 400ms (through the score pop),
   and the next wobble starts after that. Only the primary pointer counts; `touch-action: manipulation`.
5. **Landing:** the dart lands at the crosshair position at release, **plus a bounded scatter**: a point inside a disc of
   radius *cap*, weighted toward the centre so the typical (median) offset is about a third of the cap or less. The ring
   drawn around the crosshair is that disc. Because it is a hard bound, "ring fully inside the bed" guarantees the hit.
6. **Feedback after release:** the live crosshair vanishes and a hollow ghost freezes where the game counted the release (after
   release lead is applied), ring still shown. About 0.3s later the dart dot flies from the ghost to its landing spot (about
   150ms) with a thin line between them. A chip shows the result ("T20 · 60") for about 600ms. Android gets a 15ms vibrate.
7. Skill is timing only. Luck is limited to the bounded scatter.

### Determinism rules (these protect leaderboards and replays in M3)

- Core never sees a clock. A throw's input is `{target, releaseTick}`.
- **Tick = 8ms (125 ticks per second).** The UI computes `releaseTick = floor((event.timeStamp − aimStart − leadMs) / 8)`.
  The renderer draws the crosshair at the same floored tick, so display and scoring agree. No accumulator loop: the path is a
  pure function of tick. The clock freezes on `visibilitychange` and re-arms when the tab returns.
- **No `Math.sin`, `Math.cos` or `atan2` in core.** Wobble uses a committed 1024-entry integer sine table (generated by a Node
  script, pinned by a checksum test) with integer phase accumulators. Segment lookup uses integer cross-products. Scatter uses
  rejection sampling. Reason: engines can differ in the last bit, which could flip an edge-of-bed dart on a server replay.
- Each throw's wobble phase and scatter come from `hash(seed, throwIndex)`, not from a shared random stream, and always consume
  the same number of draws. Everyone on the same seed gets the same dart for dart.
- Board coordinates are integers (1 unit = 0.1mm of a real board). Sliders show "treble widths" (1 treble width = 8mm) so
  Sam never thinks in pixels or units.
- A run log is versioned from the first tester build: `{v:1, seed, settings, throws:[{target, releaseTick}]}`.

## Lab settings and starting values

All values are starting guesses; nothing is simulated yet. Sam tunes them with the Lab. **The acceptance targets below are
the real requirement, not the slider values.**

| Setting | Range | Start |
|---|---|---|
| Wobble radius (treble widths) | 1-4 | 2.5 |
| Wobble loop time (seconds) | 0.8-2.5 | 1.6 |
| Wobble shape | figure-8 / circle | figure-8 |
| Scatter cap (treble widths) | 0-2 | 1.0 (median ~0.35) |
| Release lead (ms) | -150 to +150 | 60, then set by calibration |
| Zoom | 1.5x-3.5x | 2x |

**Acceptance targets for a first-timer** (10 darts at T20): 55%+ land in the 20 wedge, 15-25% hit T20, 90%+ land in 20/1/5.
After 10 legs: T20 about 30-40%, leg average 50-65. At least 65% of misses should be down to timing, not scatter.

## Screens

### `/lab` (Throw Lab)
- Pinned live board in the top 45% so Sam tunes while watching it wobble.
- Sliders: native range inputs in full-width rows of 56px or more, 32px thumb, 44px stepper buttons, a big live number, tap a
  label to reset it.
- **Settings in the URL:** versioned, integers only, every key written, e.g. `/lab#v1&spd=120&shp=35&sct=14&brd=250`. Updates
  are debounced 300ms with `replaceState`. Values are clamped on read and unknown keys ignored. "Share link" uses
  `navigator.share`. Release lead lives in `localStorage` and is **not** in the shared link, because it is per-phone latency.
- **"10 darts at T20" drill** reports: a picture of the 10 landings on a zoomed T20 with the ring and a line from tap to
  dart; plain counts and score ("T20 x3, S20 x4, S1 x2, S5 x1. 118"); a skill-versus-luck line ("70% of your misses were
  timing"); a one-word verdict (too loose / right / too easy) with a tip; a running tally of the last 30 darts.
- **Apply measured lead:** replay the stored release ticks through core at leads from -150 to +150ms in 4ms steps, pick the
  tightest group, show "Group 31px → 19px with +40ms" and an "Apply +40ms" button. Disabled with fewer than 8 darts or a
  gain under 10%.
- **Latency calibration:** a quick 5-tap test on first launch sets the release-lead default, so a laggy phone doesn't fail
  Gate 1 on hardware.
- **Main button: "Play a leg with these settings"**, which opens `/` with the settings frozen.

### `/` (solo 501 leg, Gate 1 build)
- Loads frozen Lab settings from the URL. 501, double out, busts, three darts a turn.
- Shows darts used and a **par** ("beat 33 darts"). Win or lose against par is the reason to throw another leg. No opponent
  in M0, so a bad result can't be blamed on one.
- After each leg: "Did darts land where you aimed? Mostly / Sometimes / Rarely" (one tap), then "Another leg".
- A 10-dart warm-up first, offering the same "apply measured lead".
- Legs, darts, averages and T20 rate are logged to `localStorage`. **"Send my results"** posts the run code, device, build id,
  settings and rating to a free form service (Tally or Formspree). **"Copy my results"** is the fallback if the post fails.

## Architecture

```
src/core/     pure TypeScript, no DOM/clock/network
  rng.ts        hash(seed, index) → draws (integer)
  tables/       sine table (generated + checksum-tested)
  board.ts      integer geometry, bed lookup (segments, doubles, trebles, bulls)
  scoring.ts    501 double-out, busts
  throw.ts      aimAt(params, tick) → crosshair; resolveThrow(params, target, releaseTick, draws) → landing + bed
  leg.ts        leg state machine (darts, remaining, bust, par)
  settings.ts   schema, clamp, URL encode/decode (integers)
  replay.ts     {seed, settings, throws} → results
src/render/   Canvas 2D: board, zoom, crosshair, ring, ghost, dart, in-throw HUD (drawn on canvas)
src/ui/       Preact: lab.html and index.html as separate entries, sliders, drill report, leg screen, feedback
scripts/      guard.mjs, gen-sin-table.mjs, analyse-runs.mjs (replays tester codes)
```

- **Rendering and UI never decide outcomes.** They send `{target, releaseTick}` to core and draw what it returns.
- **Preact**, not plain DOM: the Lab and the M1 shop are state-heavy. Never re-render Preact per frame; the in-throw HUD is
  canvas. Reversible, because core has no UI dependency.
- **Units and their contracts:** the board renderer takes a board state and a crosshair; core takes params, target and tick;
  the UI owns the clock. Each can be tested alone.

## Tester logistics (no backend)

- A long-lived `gate1` branch (never `main`) gives one stable Vercel preview URL with settings frozen into the link.
  Vercel preview protection may put a login wall in front of testers: use a shareable link and check it on a phone that isn't
  signed in.
- `/playtest-pack` writes the tester message and the 4-6 questions from the Gate 1 criteria.
- `scripts/analyse-runs.mjs` replays pasted run codes to get aim-versus-landed distance per throw, legs started, darts per
  leg and busts.
- Testers: three who know darts (pub or TV watchers) and two casual phone players, one of them on a mid-range Android. They
  all play the same single setting. A "Forgiving" preset (smaller wobble, smaller cap) stays in reserve for the fail-once week.

## Plumbing

`npm run check` = guard + lint + typecheck + Vitest. `npm run guard` (a small Node script) fails on: `Math.random`, `Date.now`,
`Math.sin`, `Math.cos`, `atan2` in `src/core/`; and a short banned-terms list (real players, PDC, WDF, Sky, Ally Pally,
Premier League) in source and content. CI already runs `check` and the Playwright test when a config exists. Playwright: one
mobile smoke test (390x844) that loads `/` and `/lab`, throws a dart, and saves screenshots. Vercel previews on every PR.

## Error handling

- Bad or missing URL settings: clamp and fall back to defaults, never throw.
- `localStorage` unavailable (private tabs): the game works, the results panel says progress isn't saved.
- Form post fails: show "Copy my results" instead.
- Tab hidden mid-aim: the clock freezes and the wobble restarts on return, so no dart fires by accident.

## Testing

Each task has a test written first (Vitest unless noted).
- **Replay:** same seed + settings + throws always gives the same result, checked against a committed golden file.
- **Cross-engine replay:** the same golden replay runs in Chromium and WebKit through Playwright (WebKit stands in for
  iPhone Safari), to catch float or table differences.
- Sine table checksum; board lookup at every bed edge; 501 double-out and bust rules; bounded scatter never exceeds the cap;
  scatter always consumes the same number of draws; URL settings round-trip and clamp; release guards (re-aim lockout, throw
  lockout).
- Guard script tests (it catches the banned items, and passes clean code).
- Mobile screenshots of `/` and `/lab` at 390x844, reviewed by `mobile-playtester` before the PR.
